# migrations — DBを「どこでも建て直せるレシピ」

今日 SQL Editor で手で打った変更を、**順番つきのファイル**にまとめたもの。
これが「マイグレーション」。空っぽのDBに上から順に流すと、同じ構造が再現される。

## ファイル（必ずこの順で実行）
1. `001_create_tweets.sql` … tweets表を作る（第3章）
2. `002_add_user_id_and_rls.sql` … user_id を足して RLS で守る（第4章）
3. `003_public_timeline.sql` … is_public を足して公開タイムライン（第6章）
4. `004_create_follows.sql` … フォロー関係の中間テーブル（第7章）
5. `005_semantic_search.sql` … pgvectorで「意味検索」（embedding列＋match_tweets関数）

## 使い方（新しいSupabaseプロジェクトに同じDBを建てる）
1. 新しいプロジェクトを作る
2. SQL Editor で `001` の中身を貼って Run → `002` → `003` → `004` → `005` の順に流す
3. これで構造（テーブル・列・RLSポリシー）が完全に再現される

## 大事な区別
- **このレシピが再現するのは「構造（スキーマ）」だけ** … テーブル・列・ポリシー
- **データ（ツイートの中身）は別物** … バックアップ/エクスポートで運ぶ
- たとえ：間取り図（migrations）は同じ家を建てられるが、家具（データ）は別に運び込む

## なぜ価値がある？
- DBの構造が「コード」になる → Gitで履歴管理・レビュー・どこでも再現
- 「自分のPC → 本番」「新メンバー参加」「作り直し」でも、同じ手順で同じ箱が建つ

> 今日のDBは 001→004 を1つずつ手で実行して育てたのと同じ。だから現状＝このレシピを流した結果と一致する。
